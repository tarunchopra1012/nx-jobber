## General Guidelines for working with Nx

- For navigating/exploring the workspace, invoke the `nx-workspace` skill first - it has patterns for querying projects, targets, and dependencies
- When running tasks (for example build, lint, test, e2e, etc.), always prefer running the task through `nx` (i.e. `nx run`, `nx run-many`, `nx affected`) instead of using the underlying tooling directly
- Prefix nx commands with the workspace's package manager (e.g., `pnpm nx build`, `npm exec nx test`) - avoids using globally installed CLI
- You have access to the Nx MCP server and its tools, use them to help the user
- For Nx plugin best practices, check `node_modules/@nx/<plugin>/PLUGIN.md`. Not all plugins have this file - proceed without it if unavailable.
- NEVER guess CLI flags - always check nx_docs or `--help` first when unsure

## Scaffolding & Generators

- For scaffolding tasks (creating apps, libs, project structure, setup), ALWAYS invoke the `nx-generate` skill FIRST before exploring or calling MCP tools

## When to use nx_docs

- USE for: advanced config options, unfamiliar flags, migration guides, plugin configuration, edge cases
- DON'T USE for: basic generator syntax (`nx g @nx/react:app`), standard commands, things you already know
- The `nx-generate` skill handles generator discovery internally - don't call nx_docs just to look up generator syntax

## Prisma 7 setup already in place — DO NOT revert these

- `schema.prisma`: generator `provider = "prisma-client"`, `moduleFormat = "cjs"`,
  `importFileExtension = ""`, output into the source tree; datasource has NO `url`.
- `prisma.config.ts`: holds the datasource `url` from `process.env.DATABASE_URL`
  (NOT prisma's strict `env()` helper), and loads `.env` via a guarded
  `process.loadEnvFile()` (tolerates a missing `.env` in CI).
- `PrismaService`: `super({ adapter: new PrismaPg({ connectionString:
configService.getOrThrow<string>('DATABASE_URL') }) })`. It takes `ConfigService`
  through the constructor rather than reading `process.env` directly, because the
  running service gets its values from `ConfigModule`. Import PrismaClient via a
  RELATIVE path to the generated folder (not a bare specifier, not `node_modules`).
- `app.module.ts`: `ConfigModule.forRoot({ isGlobal: true })` loads the root `.env`
  for the running service (matches the author's repo). `main.ts` must NOT call
  `process.loadEnvFile()` — only `prisma.config.ts` still does, because the Prisma
  CLI runs outside the Nest DI container. Values reach the app via `ConfigService`.
- `project.json`: `build` and `test` both `dependsOn: ["generate-types"]`;
  `migrate-prisma` runs `prisma migrate dev --name {args.name}` (default `init`).
- The generated Prisma client is git-ignored and regenerated by `generate-types`.
- CI (`.github/workflows/ci.yml`) runs `nx affected -t lint test build` and must
  work on a clean checkout (no `.env`, no generated client).

## GraphQL / Apollo (Apollo Server 5)

- `@as-integrations/express5` is a REQUIRED runtime dependency. Apollo Server 4
  bundled `@apollo/server/express4`; v5 removed it, and `@nestjs/apollo@13`
  lazily `require`s the integration at bootstrap. Without it the build succeeds
  and Nest fails at `GraphQLModule` init with a `PackageLoader` error.
- The `@apollo/server-plugin-landing-page-graphql-playground@4` peer warning
  during `npm install` is a transitive dep of `@nestjs/apollo`; ignore it.

## Nx test targets

- `nx.json` has a `targetDefaults.test.options.passWithNoTests: true`. The
  `@nx/jest` plugin infers a `test` target for EVERY project, so any lib without
  spec files (e.g. `libs/nestjs`) fails CI with "No tests found" otherwise.
- Nx generators scaffold `*.spec.ts` files that only register the class under
  test. As soon as a class gains a constructor dependency, its generated spec
  must be given a mock provider or CI fails with a Nest DI resolution error.

## What to do when the video and reality disagree

When I paste an error (or say "the video said X but it fails"):

1. Identify the relevant file(s) in MY local repo.
2. Fetch the corresponding file(s) from the author's GitHub repo (raw URL).
3. Diff three things: what the video showed, what the author's repo has now, and
   what my local code has.
4. Recommend the fix that matches the author's Prisma 7 ARCHITECTURE but is
   ADAPTED to my newer tooling. Explain _why_ it broke (which version/feature),
   not just the fix.
5. Never undo the Prisma 7 adaptations listed above.
6. Prefer minimal, surgical changes. If a fix is environmental (Node version,
   docker-compose creds, missing `.env`), say so instead of changing code.

When you need info, ask me for the exact error text and which lesson/feature
I'm on. Assume the author's repo may be AHEAD of my current lesson, so only apply
what's relevant to where I am.
